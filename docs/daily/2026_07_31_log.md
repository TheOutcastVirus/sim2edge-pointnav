# 2026-07-31 — Removing the odometry input

Yesterday's PPO run finished at 94.5% success. Today started as adversarial
testing of that policy and turned into a design change: **the deployed policy
should navigate from a relative goal using lidar and an IMU, with no odometry
input.** This log records what the current policy actually is, the three
measurements that changed the plan, the options considered, and what was built.

Adversarial testing is deferred and now depends on this work — the reason is in
[Why the adversarial plan changed](#why-the-adversarial-plan-changed).

---

## 1. What the trained policy actually consumes

Verified directly against `runs/ppo_v1/best.pt`, offline, not read off the code.

| Block | Width | Contents |
|---|---:|---|
| lidar | 4 × 180 = 720 | 360° scan, min-pooled into bins, normalized to [0,1]; `INVALID_FILL = 1.0` for no-return |
| goal | 3 | `(dist / 8.0, sin bearing, cos bearing)`, **robot frame** |
| previous action | 4 × 2 = 8 | last four commanded `(v, ω)`, normalized |
| **total** | **731** | 290,610 parameters |

Output is physical `(v, ω)` in SI, tanh-squashed to the Create3 envelope.

**Yes, it takes a (Δx, Δy) and navigates on lidar alone.** `goal_features()`
subtracts pose from goal and rotates into the body frame, so the goal input *is*
a relative offset in polar form. The only exteroceptive input is lidar. No
camera, no map, no global pose. Empty-room response is correctly signed and
symmetric: goal at +90° → ω = +0.74, at −90° → ω = −0.80, at ±45° → ω = ±0.57.

**The caveat that started all of this:** the goal is recomputed *every tick* from
the current pose. It is not a fire-once waypoint. On hardware that requires
odometry good enough to keep the relative goal updated at 20 Hz. Removing that
dependency is the goal of this work.

Also worth recording: distance saturates at `GOAL_MAX_M = 8`, so `(8,0)` and
`(20,0)` produce a bit-identical observation. Any target beyond 8 m needs an
outer waypoint loop regardless of what happens with odometry.

## 2. Three measurements that changed the plan

### 2.1 The odometry noise model was white, not drift

`corrupt_goal` drew a fresh i.i.d. Gaussian every sample. Real odometry error is
a **random walk**: it integrates and never comes back. White noise has zero
autocorrelation, so it averages out across the four-frame history and the policy
can low-pass it away for free.

This is not a modelling nicety. Every odometry-robustness number this project has
reported was measured against an error that could be shaken off. Measured
autocorrelation at lag 1 within an episode, before and after the fix:

| | lag-1 autocorrelation | xy error at episode end | yaw error at episode end |
|---|---:|---:|---:|
| old (i.i.d.) | ~0.00 | — | — |
| new (random walk) | **0.995** | 6.7 cm mean / 13.3 cm p95 | 0.97° mean / 2.26° p95 |

### 2.2 The supervision needed was already in the corpus

`dataset.py` stores `pose (T,3)` true world x/y/yaw and `episode` ids. Body-frame
ego-motion between consecutive steps is a subtraction and a rotation away, and
the gyro is derivable from the same poses. **No recollection was needed** — the
104 GB of `overnight_v2` survives this change intact, because the new sensor
models are applied at load time like the existing noise.

### 2.3 The policy's own lidar input is too coarse to do odometry with

180 bins is 2° per bin. At a typical ω = 0.5 rad/s, per-step yaw change is
0.025 rad ≈ **1.4°, below one bin**. Scan-matching on the policy's input would be
quantization-limited from the start. The raw scan is 720 beams at 0.5°
(`nav_task.py:96`), stored in the shards, and available in C++ on the robot.

This is what made the IMU decisive rather than merely convenient: lidar is bad at
exactly the thing the gyro is good at.

## 3. The reframe

**You cannot delete the information, only relocate the estimator.**

The relative goal at time *t* is the goal at *t = 0* composed with everything the
robot has moved since. Arrival detection is the hard part: the policy must know
it is within 0.25 m of a thing it cannot see, and nothing in a lidar scan says
"the goal is here" — the goal is not a physical object.

So "no odometry input" means *no wheel-encoder/EKF input*. The estimator moves
inside the model, fed by the only two things left: the lidar, and the commands
issued.

**Every option below is recurrent.** Anything maintaining a goal belief across an
episode carries state; that is forced by the task. What differs is how much
structure the update carries.

## 4. Options considered

| | State | Update rule | End-to-end |
|---|---|---|---|
| **A** — command dead reckoning | goal vector | exact, from commanded `(v, ω)` | n/a (no learning) |
| **B** — lidar-odometry head | goal vector | exact composition; learned Δ | only if trained jointly |
| **B-joint** ← **chosen** | goal vector | exact composition; learned Δ, BPTT | yes |
| **C** — recurrent policy (GRU) | opaque hidden vector | fully learned | yes |
| **D** — semantic recurrence | goal vector | fully learned | yes |

### A — Command dead reckoning

Integrate the goal from commanded `(v, ω)`. Zero architecture change. Still
odometry, just from actuation rather than a sensor; its error is command-tracking
error. Kept as the baseline every other option must beat — and, as it turns out,
**nested inside the chosen design** (§5.2).

### C — Recurrent policy, goal shown once

A GRU learning the belief end-to-end. The only option that could learn *implicit
loop closure* — recognizing a previously-seen wall and correcting. Rejected for
now on three counts: it collides with the constraint written into `spec.py:97`
(four frames were chosen to avoid recurrent state in the deployed graph); INT8
quantization accumulates error through a recurrence, which was the original
reason for that constraint; and it makes debugging much worse, because a
navigation failure and a localization failure become indistinguishable.

### D — Semantic recurrence

Policy emits `(v, ω, ĝ_next)`, with `ĝ` fed back. A GRU whose hidden state is
forced to be the goal vector — interpretable, supervisable, resettable. Held in
reserve: it is where to go if B-joint's geometric bottleneck costs accuracy. Its
cost is compounding error at rollout, needing scheduled sampling or DAgger.

### B-joint — chosen

State is the goal vector; the update is the composition that offset provably
obeys; rotation comes from the gyro; only the translation residual is learned.
Trained end-to-end with BPTT through the recurrence.

## 5. What was built

### 5.1 The composition

```
g_{t+1} = R(-Δθ_t) · (g_t - Δp_t)
```

Exact, derived in `models/belief.py`. Verified to 2.2 × 10⁻⁵ m accumulated
float32 error over 200 steps with exact inputs (relative error 4 × 10⁻⁶).

### 5.2 The translation head predicts a residual, not a displacement

```
Δp_t = (v_cmd · DT, 0) + correction(lidar history, gyro, previous commands)
```

Three consequences, and they are the reason for this shape:

* **Option A is the zero-weights special case.** The baseline is nested inside
  the model, so training starts at baseline quality and cannot accidentally do
  worse. Verified: at initialization the correction is 4.3 × 10⁻⁵ m against a
  2.3 cm commanded tick — 0.19%.
* **Degradation is graceful where it must be.** In open space where all returns
  exceed max range, lidar ego-motion is genuinely unobservable. A residual model
  falls back to dead reckoning there on its own.
* The correction is small and zero-centred — a far easier regression target than
  an absolute displacement dominated by its own mean.

Lateral output is scaled to 15% of forward: differential drive cannot translate
sideways, so lateral motion is wheel slip, a residual on a residual.

### 5.3 Rotation is the gyro's, unmodified

Measured integrated heading error over a 190-step episode: **0.45° mean, 1.07°
p95** on a realistic varying-rate trajectory; under 2° in the worst case of
sustained one-directional rotation, where the scale-factor term does not cancel.

That is 2.3 cm of lateral error at 3 m remaining, against a 0.25 m goal
tolerance. Wheel-odometry yaw — the thing being removed — is worth several
degrees. **Yaw stops being the binding constraint**, which is what makes this
tractable rather than a research problem.

Gyro model is three terms: angle random walk (negligible, ~0.03°/episode, modelled
so its negligibility is demonstrated), a per-episode bias after calibration
(dominant), and a per-episode scale error (proportional to rotation, punishes
cornering). Accelerometer is **not** used for translation — double integration
drifts as *t*² and is worthless over 10 s.

### 5.4 The actor observation is byte-identical, deliberately

The obvious design feeds the gyro to the actor. That widens the trunk input and
orphans every trunk weight in `runs/ppo_v1/best.pt` — 300 PPO iterations and the
whole BC corpus behind them.

Routing the gyro to the odometry head *only* costs the actor nothing it cannot
already infer, and buys a complete warm start. Verified: the actor loads strictly
from `runs/ppo_v1/best.pt` and is numerically identical to the standalone policy
(max difference 0.0), and belief-derived goal features match pose-derived ones
exactly (max difference 0.0).

The single randomly-initialized module in the new model is the odometry head.
595,764 parameters total; 305,154 of them new.

### 5.5 The spinning lidar

The old model treated the A1 as an instantaneous 720-beam snapshot every control
tick. Neither half is true:

* One revolution at 5.5 Hz takes **182 ms = 3.6 control periods**, so a scan is
  stitched from beams acquired at three or four different poses — motion skew,
  and the skew is a function of the command just issued. Worst exactly when the
  robot turns hard to avoid something.
* A complete fresh revolution is not available every tick. Beam age varies
  continuously with bearing, from 0 to 182 ms.

`sensors.sweep_scan` stitches a revolution from `SPIN_TICKS = 5` stored scans,
each beam drawn from whichever is nearest its own acquisition time. The skew is
*implicit* — no reprojection, no appeal to ground-truth pose, because the raw
return really was produced at that pose and presenting it at the nominal bearing
is precisely the error the hardware makes.

`sensors.deskew` is what the robot does about it: gyro for rotation (exact under
constant rate — pinned by test), commanded speed for translation. This is fixed,
non-learned preprocessing in the same category as `bin_lidar`; it does not make
the policy less end-to-end, it declines to spend capacity relearning a rotation
matrix that is exactly known.

**Spin rate is `LIDAR_SPIN_HZ = 5.5` in `spec.py`. Confirm what the unit is
actually configured to** — the A1 motor is PWM-adjustable toward ~10 Hz, and
every sim2real number depends on this constant.

### 5.6 Fingerprints: shards survive, checkpoints do not

Spin rate and deskew go in `observation_fingerprint`, not `fingerprint`. Shards
hold clean instantaneous ranges and true poses; the sweep is *reconstructed* from
them at load time, so no stored byte changed. Old checkpoints are correctly
rejected, with `allow_legacy_sensor_model=True` as an explicit, non-silent escape
hatch — needed because running the old policy against the corrected sensor model
is the measurement that says what the correction was worth.

## 6. Three bugs found during implementation

All three were invisible in shapes and in loss curves, and all three would have
read as "the odometry head doesn't work."

### 6.1 The belief integrated two different ticks

The gyro increment is backward-looking (t−1 → t); the commanded translation was
forward-looking (t → t+1). Mixing them cost **8 cm of belief error at
initialization**, where dead reckoning should be near-exact.

The fix is that *everything* looks backward: `update_belief` integrates the
rotation just measured against the command just executed, both of which the robot
has right now. No lookahead anywhere. The commanded speed is read from the newest
previous-action frame rather than passed separately, so there is exactly one copy
of it.

Belief error at initialization, before and after:

| | t=7 | t=15 | t=31 |
|---|---:|---:|---:|
| before | 8.4 cm | 8.4 cm | 9.2 cm |
| after | **0.07 cm** | **0.16 cm** | **0.28 cm** |

Also fixed: `step()` now updates then acts. Acting first leaves the actor one
tick behind the sensors for the whole episode.

### 6.2 A zero-initialized head starves everything upstream

Initializing the residual head's final layer to exactly zero — the tempting way
to start at dead reckoning — makes the gradient reaching the trunk `Wᵀ·grad = 0`.
The convolutional stack received **no gradient at all** on the first step. Fixed
with `uniform_(-1e-3, 1e-3)`, matching `NavPolicy.action_head`: initial correction
0.19% of a commanded tick, and differentiable from step one.

### 6.3 Loss coefficients were meaningless because the losses had units

Translation error is ~5 × 10⁻⁴ m, so its squared loss is ~3 × 10⁻⁷ — against an
action loss of ~5 × 10⁻². At `translation_coef = 50` the head received a gradient
**3500× smaller** than the actor's, and every printed number looked reasonable.

Both geometric losses are now divided by a characteristic length before squaring:
translation by the distance one full-speed tick covers, belief by the goal
tolerance — the length at which an error stops being cosmetic and starts losing
episodes. Effect on 400 smoke steps: translation loss reduction went from 8% to
**24%**.

## 7. The blocker: the simulator has no wheel slip

**This was the most important finding of the day, and it invalidated the design's
trainability until fixed.**

`_apply_action` writes the integrated command straight to the root pose, so PhysX
never gets a say. Measured on the collected corpus:

| Measurement | Result |
|---|---:|
| `corr(commanded, achieved forward)` | 0.999621 |
| residual std per tick | **0.22 mm** |
| lateral motion std | 0.26 mm |
| lidar range noise, for scale | 20 mm |

The odometry head exists to correct dead reckoning. Dead reckoning was already
exact, and the residual the head was asked to predict sat **~90× below the
lidar's own range noise**. The head had nothing to learn, would have trained to
zero, and would have looked perfect in simulation while contributing nothing on a
robot whose wheels really do slip on carpet.

A design whose whole purpose is to correct dead reckoning cannot be validated in
a world where dead reckoning is already perfect.

Fixed in two places:

* **`nav_task._apply_action`** now applies slip to the pose integration (not to
  the command the policy reads back — a robot knows what it asked for, only the
  floor knows what it got). Per-episode systematic term, per-substep random term,
  and a turn-dependent term because skid-steer scrubs. Gated by `NavEnvCfg.wheel_slip`,
  default on.
* **`dataset._slip`** introduces the same gap at load time for the existing
  corpus, which was collected without it. The stored pose stays truth and the
  dead-reckoned command is inflated by the slip that would have produced that
  motion. This is a stand-in, honest only because it has the same multiplicative
  structure real slip does.

**The real fix is recollection against the corrected simulator.** Until then the
load-time augmentation is what makes the head trainable.

## 8. Why the adversarial plan changed

The existing `runs/ppo_v1/eval.json` (94.5% clean, 91.0% at 2× noise) is
held-out layouts from the same generator — in-distribution generalization, not
adversarial. Nothing in it stresses geometry the policy never saw.

More importantly, two of the three gaps found today mean **the old simulator
could not have validated an odometry-free design at all**: it delivered
instantaneous 20 Hz scans and perfect command tracking. A policy would have
looked excellent in sim and fallen over on hardware, with no way to see it
coming. Modelling the spinning sensor and wheel slip was a prerequisite, not a
follow-up.

Adversarial testing now runs against a simulator that models the sensor
honestly. The axes still to build: OOD geometry (corridors, dead-end traps,
narrow gaps near the 0.36 m body diameter, concave U-traps), goal-space stress
(saturation past 8 m, unreachable goals, tolerance-boundary goals), sector
dropout and systematic bearing offset, and timing mismatch.

One finding from the static probes is worth carrying into that work: the policy's
per-element input-gradient magnitude splits `prev_action 1.037` / `goal 0.388` /
`lidar 0.017`. Lidar is 720 elements against 8, so the totals are closer than
that looks, but the policy leans hard on its own action history — exactly what
breaks under actuator lag or dropped control ticks.

## 9. Known limits

* **Open space is unobservable.** Where every return exceeds max range, all bins
  read 1.0 and lidar ego-motion carries no information. In a long featureless
  corridor the along-corridor component is unobservable — the aperture problem.
  No architecture fixes either. The residual design falls back to dead reckoning;
  a confidence output so the outer loop knows the belief is stale is not built yet.
* **Drift is unbounded without loop closure.** Nothing here recognizes a
  previously-seen wall. Over a ~10 s episode that is acceptable; it does not
  extend to long missions.
* **Sweep quantization.** Beam acquisition time is rounded to the nearest stored
  tick, costing at most 25 ms of age against beam ages spanning 182 ms. The
  alternative is re-raycasting per sector, for an error already well under the
  range noise.
* **The corpus slip is synthetic.** See §7.

## 10. Status: ready to train

Full suite: **221 passed, 2 skipped** (175 pre-existing, 46 new across
`test_sensors.py`, `test_belief.py`, `test_noise_walk.py`,
`test_sequence_data.py`).

Smoke run on `data/postfix_verify` (29,204 samples, single shard), 395 steps,
27 s on CPU — trains end to end, warm-starts cleanly, losses move in the right
direction:

```
[belief] 595,764 parameters (305,154 in the new odometry head)
[belief] step      1  loss 0.0575  action 0.0573  belief_err 0.82 cm  drift/m 3.06 cm/m
[belief] step    380  loss 0.0351  action 0.0090  belief_err 0.97 cm  drift/m 3.29 cm/m
```

The action loss falls 6× as the actor adapts to swept scans. Belief error is
roughly flat on this corpus — expected, since it is the smallest shard available
and the head is being asked to learn a correction from 29k samples.

To launch the real run:

```bash
.venv/bin/python scripts/train_belief.py \
    --data data/bc_dagger_v1 \
    --warm-start runs/ppo_v1/best.pt \
    --out runs/belief_v1
```

**The number to watch is `belief_error_final_m`** — mean metres of goal-belief
error after a full 32-step window of the model integrating its own estimate.
Dead reckoning alone is the value at step zero; anything below that is the lidar
doing work. `drift_per_m` is the portable version, independent of window length.

Sanity floor: goal tolerance is 0.25 m. A belief error approaching that is a
policy that cannot reliably tell it has arrived.

### Open decisions before the full run

1. **Spin rate** — confirm the A1's configured rate (§5.5).
2. **Recollection** — whether to rerun collection against the slip-corrected
   simulator before or after a first belief run. The load-time stand-in works;
   real slip is better.
3. **Sequence length** — 32 steps is 1.6 s. If drift is dominated by compounding
   rather than per-step accuracy, this wants to be longer.
4. **Frozen actor** — `--freeze-actor` trains only the head. Worth one run to
   isolate whether the actor's adaptation to swept scans and the head's learning
   are interfering.
