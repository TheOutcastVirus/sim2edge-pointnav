# 2026-07-31 — Removing the odometry input

Yesterday's PPO run finished at 94.5% success. Today started as adversarial
testing of that policy and turned into a design change: **the deployed
policy should navigate from a relative goal using lidar and an IMU, with no
odometry input.** Adversarial testing is deferred — see [§8](#8-why-the-adversarial-plan-changed).

---

## 1. What the trained policy actually consumes

Verified directly against `runs/ppo_v1/best.pt`, offline, not read off code.

| Block | Width | Contents |
|---|---:|---|
| lidar | 4 × 180 = 720 | 360° scan, min-pooled into bins, normalized to [0,1]; `INVALID_FILL = 1.0` for no-return |
| goal | 3 | `(dist / 8.0, sin bearing, cos bearing)`, **robot frame** |
| previous action | 4 × 2 = 8 | last four commanded `(v, ω)`, normalized |
| **total** | **731** | 290,610 parameters |

Output is physical `(v, ω)` in SI, tanh-squashed to the Create3 envelope.

**Yes, it takes a (Δx, Δy) and navigates on lidar alone.** `goal_features()`
subtracts pose from goal and rotates into the body frame — the goal input
*is* a relative offset in polar form, and the only exteroceptive input is
lidar (no camera, no map, no global pose). Empty-room response is correctly
signed and symmetric: goal at +90° → ω = +0.74, at −90° → ω = −0.80, at ±45°
→ ω = ±0.57.

**The caveat that started this:** the goal is recomputed *every tick* from
the current pose, not a fire-once waypoint — on hardware that needs
odometry good enough to keep it updated at 20 Hz. Removing that dependency
is the goal here. Also: distance saturates at `GOAL_MAX_M = 8`, so `(8,0)`
and `(20,0)` are bit-identical; any target beyond 8 m needs an outer
waypoint loop regardless.

## 2. Three measurements that changed the plan

### 2.1 The odometry noise model was white, not drift

`corrupt_goal` drew a fresh i.i.d. Gaussian every sample. Real odometry error
is a **random walk** that integrates and never comes back; white noise has
zero autocorrelation and the policy can low-pass it away for free. Every
odometry-robustness number this project has reported was measured against an
error that could be shaken off.

| | lag-1 autocorrelation | xy error at episode end | yaw error at episode end |
|---|---:|---:|---:|
| old (i.i.d.) | ~0.00 | — | — |
| new (random walk) | **0.995** | 6.7 cm mean / 13.3 cm p95 | 0.97° mean / 2.26° p95 |

### 2.2 The supervision needed was already in the corpus

`dataset.py` stores true world `pose (T,3)` and `episode` ids — body-frame
ego-motion between steps is a subtraction and rotation away, and gyro is
derivable from the same poses. **No recollection needed**: `overnight_v2`
(104 GB) survives intact, since the new sensor models apply at load time
like existing noise.

### 2.3 The policy's own lidar input is too coarse to do odometry with

180 bins is 2°/bin. At a typical ω = 0.5 rad/s, per-step yaw change is
0.025 rad ≈ **1.4°, below one bin** — scan-matching on the policy's input
would be quantization-limited from the start. The raw 720-beam/0.5° scan is
stored in shards and available in C++ on the robot. This is what makes the
IMU decisive: lidar is bad at exactly what the gyro is good at.

---

## 3. The reframe

**You cannot delete the information, only relocate the estimator.** The
relative goal at time *t* is the goal at *t=0* composed with everything the
robot has moved since. Arrival is the hard part: the policy must know it is
within 0.25 m of something it cannot see. So "no odometry input" means *no
wheel-encoder/EKF input* — the estimator moves inside the model, fed only by
lidar and issued commands. Every option below is therefore recurrent; what
differs is how much structure the update carries.

## 4. Options considered

| | State | Update rule | End-to-end |
|---|---|---|---|
| **A** — command dead reckoning | goal vector | exact, from commanded `(v, ω)` | n/a (no learning) |
| **B** — lidar-odometry head | goal vector | exact composition; learned Δ | only if trained jointly |
| **B-joint** ← **chosen** | goal vector | exact composition; learned Δ, BPTT | yes |
| **C** — recurrent policy (GRU) | opaque hidden vector | fully learned | yes |
| **D** — semantic recurrence | goal vector | fully learned | yes |

**A** — zero architecture change; still odometry, just from actuation
instead of a sensor. Kept as the baseline every option must beat, and turns
out to be nested inside the chosen design (§5.2).

**C** — the only option that could learn implicit loop closure. Rejected:
collides with the no-recurrent-state constraint in `spec.py:97` (originally
to keep INT8 quantization error from accumulating through a recurrence), and
makes debugging worse since navigation and localization failures become
indistinguishable.

**D** — policy emits `(v, ω, ĝ_next)` fed back; a GRU whose hidden state is
forced to be the goal vector, interpretable and resettable. Held in reserve
if B-joint's geometric bottleneck costs accuracy; costs compounding rollout
error needing scheduled sampling or DAgger.

**B-joint (chosen)** — state is the goal vector, update is the composition
the offset provably obeys, rotation from the gyro, only the translation
residual is learned. Trained end-to-end with BPTT through the recurrence.

## 5. What was built

### 5.1 The composition

```
g_{t+1} = R(-Δθ_t) · (g_t - Δp_t)
```

Exact, in `models/belief.py`. Verified to 2.2 × 10⁻⁵ m accumulated float32
error over 200 steps with exact inputs (relative error 4 × 10⁻⁶).

### 5.2 The translation head predicts a residual, not a displacement

```
Δp_t = (v_cmd · DT, 0) + correction(lidar history, gyro, previous commands)
```

Three consequences:

* **Option A is the zero-weights special case** — the baseline is nested in
  the model, so training starts at baseline quality. Verified: at init the
  correction is 4.3 × 10⁻⁵ m against a 2.3 cm commanded tick (0.19%).
* **Degradation is graceful where it must be.** In open space, where all
  returns exceed max range, lidar ego-motion is genuinely unobservable and
  the residual model falls back to dead reckoning on its own.
* The correction is small and zero-centred — an easier regression target
  than an absolute displacement dominated by its own mean.

Lateral output is scaled to 15% of forward, since differential drive cannot
translate sideways — lateral motion is wheel slip, a residual on a residual.

### 5.3 Rotation is the gyro's, unmodified

Measured integrated heading error over 190 steps: **0.45° mean, 1.07° p95**,
under 2° even in the worst case (sustained one-directional rotation, where
the scale-factor term does not cancel) — 2.3 cm of lateral error at 3 m
remaining, against a 0.25 m goal tolerance. Wheel-odometry yaw (what's being
removed) is worth several degrees, so **yaw stops being the binding
constraint**, which is what makes this tractable.

Gyro model: angle random walk (negligible, ~0.03°/episode), a per-episode
bias after calibration (dominant), a per-episode scale error (proportional
to rotation, punishes cornering). Accelerometer is **not** used for
translation — double integration drifts as *t*² and is worthless over 10 s.

### 5.4 The actor observation is byte-identical, deliberately

Feeding the gyro to the actor directly would widen the trunk input and
orphan every trunk weight in `runs/ppo_v1/best.pt` (300 PPO iterations plus
the whole BC corpus). Routing the gyro to the odometry head only costs the
actor nothing it can't already infer, and buys a complete warm start.
Verified: the actor loads strictly from `runs/ppo_v1/best.pt`, numerically
identical to the standalone policy (max diff 0.0); belief-derived goal
features match pose-derived ones exactly (max diff 0.0). The odometry head
is the only randomly-initialized module: 595,764 parameters total, 305,154
new.

### 5.5 The spinning lidar

The old model treated the A1 as an instantaneous 720-beam snapshot every
control tick — neither half true. One revolution at 5.5 Hz takes
**182 ms = 3.6 control periods**, so a scan is stitched from beams acquired
at three or four different poses (motion skew, worst exactly when the robot
turns hard to avoid something), and a complete fresh revolution isn't
available every tick — beam age varies continuously from 0 to 182 ms.

`sensors.sweep_scan` stitches a revolution from `SPIN_TICKS = 5` stored
scans, each beam drawn from whichever is nearest its acquisition time. The
skew is *implicit* — no reprojection or ground-truth appeal, since the raw
return really was produced at that pose. `sensors.deskew` is what the robot
does about it: gyro for rotation (exact under constant rate, pinned by
test), commanded speed for translation — fixed, non-learned preprocessing
like `bin_lidar`.

**Spin rate is `LIDAR_SPIN_HZ = 5.5` in `spec.py`. Confirm what the unit is
actually configured to** — the A1 motor is PWM-adjustable toward ~10 Hz, and
every sim2real number depends on this constant.

### 5.6 Fingerprints: shards survive, checkpoints do not

Spin rate and deskew go in `observation_fingerprint`, not `fingerprint`.
Shards hold clean instantaneous ranges and true poses; the sweep is
reconstructed at load time, so no stored byte changed. Old checkpoints are
correctly rejected, with `allow_legacy_sensor_model=True` as an explicit
escape hatch — needed to measure what the old policy does against the
corrected sensor model.

## 6. Three bugs found during implementation

All three were invisible in shapes and loss curves and would have read as
"the odometry head doesn't work."

### 6.1 The belief integrated two different ticks

The gyro increment is backward-looking (t−1→t); commanded translation was
forward-looking (t→t+1). Mixing them cost **8 cm of belief error at
initialization**, where dead reckoning should be near-exact. Fix: everything
looks backward — `update_belief` integrates the rotation just measured
against the command just executed. `step()` now updates then acts (acting
first left the actor one tick behind for the whole episode).

| | t=7 | t=15 | t=31 |
|---|---:|---:|---:|
| before | 8.4 cm | 8.4 cm | 9.2 cm |
| after | **0.07 cm** | **0.16 cm** | **0.28 cm** |

### 6.2 A zero-initialized head starves everything upstream

Initializing the residual head's final layer to exactly zero — tempting, to
start at dead reckoning — makes `Wᵀ·grad = 0`: the conv stack received no
gradient at all on step one. Fixed with `uniform_(-1e-3, 1e-3)`, matching
`NavPolicy.action_head`: initial correction 0.19% of a commanded tick,
differentiable from step one.

### 6.3 Loss coefficients were meaningless because the losses had units

Translation error is ~5×10⁻⁴ m, squared loss ~3×10⁻⁷, against an action loss
of ~5×10⁻². At `translation_coef = 50` the head received a gradient **3500×
smaller** than the actor's, and every printed number looked reasonable. Both
geometric losses are now divided by a characteristic length before squaring
(translation by one full-speed tick, belief by goal tolerance). Effect on
400 smoke steps: translation loss reduction went from 8% to **24%**.

## 7. The blocker: the simulator has no wheel slip

**The most important finding of the day** — it invalidated the design's
trainability until fixed. `_apply_action` writes the integrated command
straight to the root pose; PhysX never gets a say.

| Measurement | Result |
|---|---:|
| `corr(commanded, achieved forward)` | 0.999621 |
| residual std per tick | **0.22 mm** |
| lateral motion std | 0.26 mm |
| lidar range noise, for scale | 20 mm |

The odometry head exists to correct dead reckoning, but dead reckoning was
already exact and the residual it was asked to predict sat **~90× below the
lidar's own range noise** — it would have trained to zero and looked
perfect in sim while contributing nothing on a robot whose wheels really do
slip on carpet. A design whose purpose is correcting dead reckoning can't be
validated in a world where dead reckoning is already perfect.

Fixed in two places:

* **`nav_task._apply_action`** now applies slip to the pose integration
  (not the command the policy reads back — a robot knows what it asked for,
  only the floor knows what it got): per-episode systematic term, per-substep
  random term, turn-dependent term for skid-steer scrub. Gated by
  `NavEnvCfg.wheel_slip`, default on.
* **`dataset._slip`** introduces the same gap at load time for the existing
  corpus (collected without it): stored pose stays truth, the dead-reckoned
  command is inflated by the slip that would have produced that motion. A
  stand-in, honest only because it shares real slip's multiplicative
  structure.

**The real fix is recollection against the corrected simulator.** Until then
the load-time augmentation is what makes the head trainable.

## 8. Why the adversarial plan changed

`runs/ppo_v1/eval.json` (94.5% clean, 91.0% at 2× noise) is held-out layouts
from the same generator — in-distribution generalization, not adversarial.
More importantly, two of today's three findings mean **the old simulator
could not have validated an odometry-free design at all**: it delivered
instantaneous 20 Hz scans and perfect command tracking, so a policy could
look excellent in sim and fail on hardware with no way to see it coming.
Modelling the spinning sensor and wheel slip was a prerequisite, not a
follow-up.

Axes still to build: OOD geometry (corridors, dead-end traps, narrow gaps
near the 0.36 m body diameter, concave U-traps), goal-space stress
(saturation past 8 m, unreachable goals, tolerance-boundary goals), sector
dropout and systematic bearing offset, timing mismatch.

One static-probe finding worth carrying forward: per-element input-gradient
magnitude splits `prev_action 1.037` / `goal 0.388` / `lidar 0.017`. Lidar is
720 elements against 8, so totals are closer than that looks, but the policy
leans hard on its own action history — exactly what breaks under actuator
lag or dropped control ticks.

## 9. Known limits

* **Open space is unobservable.** Where every return exceeds max range, all
  bins read 1.0 and lidar ego-motion carries no information (the aperture
  problem in a long corridor). No architecture fixes this; the residual
  design falls back to dead reckoning, but a confidence output for the outer
  loop isn't built yet.
* **Drift is unbounded without loop closure.** Nothing here recognizes a
  previously-seen wall — acceptable over a ~10 s episode, doesn't extend to
  long missions.
* **Sweep quantization.** Beam acquisition time rounds to the nearest stored
  tick, up to 25 ms against ages spanning 182 ms — error stays well under
  range noise.
* **The corpus slip is synthetic.** See §7.

```bash
.venv/bin/python scripts/train_belief.py \
    --data data/bc_dagger_v1 \
    --warm-start runs/ppo_v1/best.pt \
    --out runs/belief_v1
```

**Watch `belief_error_final_m`** — mean metres of goal-belief error after a
full 32-step window of the model integrating its own estimate. Dead
reckoning alone is the value at step zero; anything below that is the lidar
doing work. `drift_per_m` is the portable version. Sanity floor: goal
tolerance is 0.25 m — belief error approaching that is a policy that can't
reliably tell it has arrived.

### Open decisions before the full run

1. **Spin rate** — confirm the A1's configured rate (§5.5).
2. **Recollection** — rerun against the slip-corrected simulator before or
   after a first belief run; the load-time stand-in works, real slip is
   better.
3. **Sequence length** — 32 steps is 1.6 s; if drift is dominated by
   compounding rather than per-step accuracy, this wants to be longer.
4. **Frozen actor** — `--freeze-actor` trains only the head, to isolate
   whether the actor's swept-scan adaptation and the head's learning are
   interfering.
