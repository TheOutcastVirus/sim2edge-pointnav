# 2026-08-04 — The actor runs on the Ventuno's NPU, and the localizer is the budget

## Outcome

`runs/body_v2_actor_prod/best.pt` is lowered to a **fully delegated** INT8
QNN `.pte` and executes on the board's Hexagon V75 at **0.15–0.18 ms**
against a 50 ms control period. Standing issues 6 and 7 from the 2026-08-03
breakthrough log are now measured rather than open.

The headline is not the actor. It was never the constraint:

| stage | board latency | share of the 50 ms period |
|---|---:|---:|
| actor, INT8 on HTP V75 | 0.15–0.18 ms | 0.4% |
| actor, portable CPU kernels | 5.15 ms | 10.3% |
| **CPU localizer, production 128/2** | **20.9–26.6 ms** | **42–53%** |

The localizer costs roughly **150×** the actor. Every remaining latency
question on this robot is a CPU scan-matching question.

## Board facts, and three that are load-bearing

Arduino Ventuno Q: **QCS8275** (`soc_id` 675, device-tree `qcom,qcs8300`),
4× Cortex-A55 + 4× Cortex-A78C, 14 GB RAM, Ubuntu 24.04, kernel
`6.8.0-1079-qcom`, ROS 2 Jazzy, QNN **2.48.0.260626**, ExecuTorch at
`/opt/executorch` commit `50529eed0a` with both inherited patches present.

### 1. ExecuTorch was built but never installed

`PyQnnManagerAdaptor.cpython-312-aarch64-linux-gnu.so` and
`libqnn_executorch_backend.so` are already built under
`/opt/executorch/build-x86` (the name is misleading — it's a native aarch64
build), and the AOT pybind is copied into the package tree. Both patches
from `docs/deployment.md` on `archive/v1-numpy-pipeline` are applied: the
`QCS8300`→`HtpArch.V75` enum and the `aarch64|arm64` pybind guard. What was
missing was only that `executorch` isn't installed into
`~/.venv/executorch` — `PYTHONPATH=/opt` makes the whole AOT toolchain
import and work. No rebuild needed.

### 2. The `aarch64-ubuntu-gcc9.4` QNN libraries do not support this SoC

This cost the most time and is not in any inherited document.
`$QNN_SDK_ROOT/lib/aarch64-ubuntu-gcc9.4/` is the obvious choice on Ubuntu
and the wrong one — its `libQnnHtp.so` rejects this silicon and ships no V75
stub at all, only `libQairtHtpV68Stub.so` and `libQnnDspV66Stub.so`:

```
<E> Dsp startup: Unsupported SoC model (SnapdragonModel): 82
<E> Invalid dsp arch. Cannot determine stub
<E> Failed to load skel, error: 4000
```

**The `82` is hardware auto-detection, not the `--soc-model` argument** —
passing `--soc-model SM8650` reports the identical `82`, ruling out the
fake-enum patch as the cause. 82 is `QNN_SOC_MODEL_QCS8300` in
`QnnTypes.h`; QNN has no `QCS8275` entry, so the chip correctly identifies
as its QCS8300-family number and the Ubuntu variant's DSP startup table
simply lacks it.

`aarch64-oe-linux-gcc11.2` supports it and ships `libQnnHtpV75Stub.so`.
Putting that directory **first** on `LD_LIBRARY_PATH` fixes device init
completely, nothing else changed:

```bash
export LD_LIBRARY_PATH=$QNN_SDK_ROOT/lib/aarch64-oe-linux-gcc11.2:$QNN_SDK_ROOT/lib/aarch64-ubuntu-gcc9.4
export ADSP_LIBRARY_PATH="$QNN_SDK_ROOT/lib/hexagon-v75/unsigned;/usr/lib/rfsa/adsp;/dsp"
```

`ADSP_LIBRARY_PATH` is semicolon-separated as inherited, and was unset on
this board. `qnn-platform-validator --backend dsp --coreVersion
--testBackend` reports Hexagon V75 and passes its unit test — the gate that
must come before trusting any number, since an HTP mismatch returns
garbage, not an error.

### 3. `padding_mode="circular"` crashes the QNN partitioner

The lidar convolutions wrap around bearing, correctly — bin 0 and bin 719
are adjacent on one revolution. But torch lowers that padding to a scatter
into an uninitialized buffer: three `dim_order_ops._empty_dim_order` (one
per conv) plus 20 `slice_copy`, 9 `slice_scatter`, 9 `copy`.
`QnnPartitioner` has no node visitor for `_empty_dim_order` and raises
`KeyError` from `is_node_supported` rather than declining the node.

`sim2edge.models.nav_policy.rewrite_circular_convolutions` writes the same
padding as an explicit wrap-around `cat` — definitionally what
`F.pad(..., mode="circular")` does — followed by a zero-padding
convolution. The graph then contains only `cat` and `convolution`, both
delegated. It's a deep copy, so training, Isaac evaluation, and every
checkpoint keep the original module and parameter names. Parity is exact
(`torch.equal`, not a tolerance) on 1024 real observations and in
`tests/test_model.py`.

## Quantization: the observer, not the bit width

The first INT8 lowering had a worst-case error of **37% of the omega
limit** that didn't improve with more bits — 8a8w, 8a8w per-channel, and
16a8w per-channel all reported max ≈ 0.70 rad/s while means fell
0.023→0.017→0.012. A tail that ignores precision isn't a resolution
problem.

Every worst sample was a hard turn near saturation (`|omega|` ≈ 1.87 of a
1.9 limit), and every one collapsed onto the *same* clamped output,
−1.1769 — the pre-tanh logit's activation range was clipping at about
±0.72. The cause: the quantizer's default activation observer tracks a
**moving average** of per-batch min/max, and the saturated turns were in
the calibration set — averaged away. Switching to a true `MinMaxObserver`:

| | omega mean | omega p99 | omega max | samples > 20% of limit |
|---|---:|---:|---:|---:|
| moving average (default) | 0.0224 | 0.424 | 0.698 | 16 / 1024 |
| **true min/max** | **0.0079** | **0.025** | **0.033** | **0 / 1024** |

Calibrating in one 1024-sample batch gives the identical number, confirming
the mechanism, but that's a coincidence of calibration set size, not the
fix — the observer choice is the fix, now default in
`scripts/lower_qnn.py` (`--moving-average-observer` restores the old
behaviour). True min/max isn't the usual advice; it's right here because
the tail *is* the operating envelope (the avoidance turns), and `tanh`
bounds the output regardless.

Production artifact, `use_16a8w --per-channel`, 373 KiB, one delegate call,
no CPU fallback:

| axis | mean error | max error |
|---|---:|---:|
| v | 0.20% of limit | 2.44% of limit |
| omega | 0.42% of limit | 1.73% of limit |

## The localizer is the control-loop budget

`scripts/bench_localizer.py` walks 1,680 real ticks from 12 held-out
episodes of `data/body_frame_v2_prod`, resetting the tracker at each
episode boundary so the submap is never stitched across a teleport. Steady
state means the submap has actually filled — the fill transient
understates the cost that matters.

Single-threaded, at the production `max_submap_scans=128 / point_stride=2`:

| submap | stride | median | p95 | share of 50 ms |
|---:|---:|---:|---:|---:|
| **128** | **2** | **20.87 ms** | 28.35 ms | **41.7%** |
| 128 | 4 | 10.41 ms | 11.38 ms | 20.8% |
| 64 | 2 | 13.18 ms | 14.91 ms | 26.4% |
| 64 | 4 | 6.66 ms | 8.41 ms | 13.3% |
| 32 | 2 | 8.65 ms | 11.43 ms | 17.3% |
| 32 | 4 | 5.12 ms | 6.83 ms | 10.2% |

A separate run of the production configuration measured 26.61 ms median —
treat 21–27 ms as the honest band. The same benchmark on the training host
is 9.51 ms, so the board is roughly 2.2–2.8× slower.

Cost is close to linear in submap size and `1/point_stride`, so there's
headroom if needed — but **latency is the only axis measured here**.
`eval_localized_submap64_2x_32.json` and `eval_localized_submap128_2x_32.json`
already exist for accuracy; nobody has yet evaluated `point_stride 4`, the
cheapest 2× on the table.

One caveat on transfer: these are simulated 720-beam sweeps with all 720
returns valid. A real RPLIDAR A1 delivers roughly half that per revolution,
so the board figure is probably pessimistic — but beam count and
`LIDAR_SPIN_HZ = 5.5` both remain unverified against the physical unit, so
this is a reason to re-measure on hardware, not to assume margin.

## What is not done

1. **The quantization gate has not been run.** The bar inherited from
   `archive/v1-numpy-pipeline` is a **sim success-rate drop under 2
   points**, not action error, precisely because a small action error can
   cost success at the moments that matter. Needs `eval_localized.py` on
   the host driving the INT8 graph — the single most important next step.
2. **Calibration is oracle-driven.** `data/body_frame_v2_prod` has
   `driver = "oracle"`; escalation #1 for a failed quantization gate is to
   recalibrate from the *deployed policy's* own state distribution.
   `scripts/dump_calibration.py` records `driver` in every calibration file
   and warns, so this stays visible rather than becoming a mystery later.
3. Preprocessing parity (Python vs C++), the ROS 2 node, and the real
   Create3 `/odom` path are untouched — standing issue 4 from 2026-08-03
   stands.
4. No robot trial. Nothing here is a sim-to-real result — it's a latency
   and numerics result on the target silicon.

## Order of work

1. Run the quantization gate on the host: `eval_localized.py` with the
   INT8 actor against the FP32 baseline, paired layouts, require under 2
   points of success-rate drop. Nothing else should be built on this
   `.pte` first.
2. If it fails, recalibrate from policy-driven observations before
   touching observers or bit widths.
3. Evaluate `point_stride 4` for accuracy — at 128 scans it halves the
   dominant cost in the loop, the only free-looking knob on the table.
4. Then the C++ node and preprocessing parity, where the inherited
   `ros_ws/src/nav_policy_node` becomes useful again.
