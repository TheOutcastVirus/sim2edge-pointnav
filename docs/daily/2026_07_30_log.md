## 2026-07-30 (latest) — Behaviour-cloning trainer and closed-loop evaluation

Phase 2 now trains directly from `data/overnight_v2`: 623 shards, 124,543,727
samples and 104 GB compressed. Concatenating that corpus would waste the 128 GB
host memory and make every epoch wait on a monolithic load, so training streams
one shard on the GPU while a single background thread inflates the next into
RAM. Four entire shards are held out; the collector emits only whole episodes,
so no adjacent timestep can cross that boundary.

The policy is a 290,034-parameter lidar CNN plus small goal/action encoders. Its
single flat input is exactly `OBS_DIM`, and its graph emits physical `(v, omega)`
through bounded in-graph scaling. A `torch.export` test pins that deployment
signature before expensive training begins.

4090 defaults are batch 8192, BF16 autocast, `torch.compile`, fused AdamW, TF32
and two corpus passes. Loss is MSE in normalized action coordinates, with a 1.5x
angular weight, so SI unit magnitudes cannot silently choose the objective.
Checkpoints include the spec fingerprint, exact dataset manifest, optimizer,
scheduler and shard cursor; resume rejects changes instead of creating a hybrid
run.

The Isaac evaluator reprocesses raw scans through the same corruption and
binning functions as the loader. Every parallel environment contributes exactly
one episode, allowing re-seeded 0x/1x/2x noise tiers to use the identical layout
vector. It reports SR, SPL, collision, timeout, time-to-goal, jerk and inference
latency.

Two integration failures were caught during bring-up: persisted NumPy 2 scalar
metrics could not be loaded in Isaac's older NumPy environment, so checkpoint
metadata is now restricted to Python scalars; and the paired-layout assertion
was exercised across two noise tiers. Final verification: **124 passed, 2
skipped**, a compiled BF16 real-shard train/validation smoke, and a successful
closed-loop Isaac rollout.

## 2026-07-30 — Invalidated collection, drive contract, 16k scaling

### The entire pre-fix collection is unusable

An independent check of `data/overnight/bc_150.npz` compared each physical
command with the pose delta it produced over roughly 998k transitions:

| Measurement | Result |
|---|---:|
| `corr(commanded omega, achieved omega)` | +0.021 |
| `corr(commanded v, achieved speed)` | -0.030 |
| mean commanded `|omega|` | 1.52 rad/s |
| mean achieved `|omega|` | 0.19 rad/s |

Median achieved yaw rate was effectively zero in every command bin, including
386k samples near -1.9 rad/s and 325k near +1.9 rad/s. Commands of 0.4--0.5 m/s
produced a median speed of 0.020 m/s, below the 0.068 m/s median while commanding
zero. One 899-step episode held `(v, omega) = (0.375, -1.31)` for 45 seconds but
moved only 7 cm and did not rotate.

The oracle labels were valid because the oracle reads the flow field. The state
distribution was not: it consisted of states visited by a base that drifted
independently of its command. All root-level `data/bc_*.npz` shards and all of
`data/overnight/` predate the fix and must never be used for training.
`data/overnight/bc_003.npz` is additionally a corrupt 170-byte partial ZIP.

### Holding the wheel-drop joints was necessary but not sufficient

The imported wheel-drop joints had previously been unactuated. They are now
held at their nominal position with high stiffness and damping, eliminating the
free suspension that unloaded wheels and created lateral slip.

Straight wheel commands then tracked, but opposing wheel speeds still scrubbed
the imported finite-width cylinder contacts instead of turning the base. That
geometry is not a tire model, and tuning actuator gains could not give it a
reliable differential-drive response.

The task action is a planar base Twist, so `Sim2EdgeNavEnv` now integrates
`(v, omega)` into an independent planar pose target at the 200 Hz physics rate
and writes the corresponding root pose and velocity. Wheel joints are still
animated from differential-drive inverse kinematics. Reset synchronizes the
planar target with the new episode pose so state cannot leak between episodes.

### Collection now refuses to start without a drive-response check

`collect_bc.py` runs a mandatory preflight before allocating the recorder or
writing a sample. It applies each of these commands for 50 ticks:

- turn in place: `(v, omega) = (0, 1.0)`;
- drive straight: `(v, omega) = (0.3, 0)`.

Achieved linear and angular response must be within 20% of the commanded axis,
with limits on cross-axis motion. `--check` uses the same assertion, so the
lightweight probe and real collection cannot diverge again. The real Isaac
check measured exactly 1.000 rad/s and 0.300 m/s.

Tests after the change: **116 passed, 2 skipped**.

### Small post-fix dataset proved the fix before scaling

`data/postfix_verify/bc_000.npz` contains 29,204 transitions from 128 episodes
(22.9 MB): 125 reached, 3 collided, and none timed out. Command response was:

| Measurement | Result |
|---|---:|
| `corr(omega)` | 0.99993 |
| `corr(v)` | 0.99962 |
| angular MAE | 0.0045 rad/s |
| linear MAE | 0.0032 m/s |

`scripts/verify_shard.py` passed every structure, label, perturbation, outcome,
observation, and load-time-noise check.

### Scaled collection to 16,384 environments

The new run uses a clean output directory and 200k-transition shards:

```bash
~/isaac-venv/bin/python scripts/collect_bc.py \
  --num_envs 16384 \
  --episodes 500000 \
  --num_layouts 512 \
  --seed 24680 \
  --sigma 0.15 \
  --shard_steps 200000 \
  --out data/overnight_v2
```

At this scale PhysX requested a `foundLostPairsCapacity` of 6,668,288. The old
`2**22` allocation would miss interactions, so `NavEnvCfg.sim` now uses
`2**23 = 8,388,608`, about 26% headroom. Any future PhysX capacity warning still
invalidates the run; it is not safe to ignore merely because collection keeps
writing.

Live verification of completed shard `bc_059.npz` found 200,110 transitions
across 786 episodes: 759 reached, 27 collided, and none timed out. The original
failure-mode calculation on 199,324 consecutive transitions gave:

| Measurement | Result |
|---|---:|
| `corr(commanded omega, achieved omega)` | 0.999913 |
| `corr(commanded v, achieved speed)` | 0.999337 |
| angular MAE | 0.004820 rad/s |
| linear MAE | 0.004301 m/s |
| mean commanded / achieved `|omega|` | 0.495 / 0.495 rad/s |

Recent completed shards arrived about every five seconds, or roughly **39--40k
kept samples/s** after warm-up. At the measurement point the collector used
about 20.4 GiB of host RAM and 11.2 GiB of RTX 4090 memory. Neither the Isaac
log nor the Isaac Lab log contained a PhysX capacity, CUDA, or out-of-memory
error after the larger buffer was applied.

For scaling comparisons, `kept-samples/s` is the primary metric because it is
actual usable-data throughput. `env-steps/s` is only gross simulator throughput.
Compare after 1,200--2,000 steps (or several completed episode waves), and also
watch the `sim`, `rec`, and `write` timing split. The progress figures are
cumulative, so early readings are not representative.
