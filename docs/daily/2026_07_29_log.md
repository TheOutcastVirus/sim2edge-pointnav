# Engineering log

Newest first. Each entry records what changed and, where it is not obvious,
*why* — the what is recoverable from git, the why is not.

## 2026-07-29 (latest) — First full collection runs; yield, memory, PhysX

The pipeline ran end to end and produced verified-good shards. Everything below
came out of running it at scale, and none of it was visible at 32 envs.

### I reported a yield figure that was wrong

I sampled a probe at step 600, when 25 of 256 environments had finished an
episode, and reported 76% yield. **Episodes that finish first are the ones that
succeed** — failures run on until they collide or hit the step cap, so they had
not been counted yet. The true figure was **8.6%**, worse than the 12% baseline,
and I told the user to launch a full run on the strength of it.

The "0 timeouts" that made it look so convincing was the same artifact: a
timeout *cannot* appear early, by construction.

**Rule:** yield is meaningless until `kept + dropped` is several multiples of
`num_envs`. Below that it always reads high.

### Collision was tested against the planning radius

`is_free` thresholded at `ROBOT_RADIUS_M = 0.18`, but the Create3's body radius
is 0.164 — the difference is deliberate planning margin. Any pose in that 16 mm
band was reported as a collision with nothing touching, and the flag is sticky
for a whole episode, so one transient graze in 900 steps discarded it.

Added `BODY_RADIUS_M = 0.164` and a separate `Room.body_free`. Deliberately *not*
in the fingerprint: it changes which episodes are selected, not how an
observation is constructed — the same reason noise ranges are excluded.

### The oracle rode the boundary it planned to

Paths ran along the 0.18 m planning edge, so tracking error crossed into the
inflated band constantly, where the flow field's recovery pushes back while the
lookahead pulls forward. That limit cycle produced episodes that both grazed
geometry and never finished — the largest failure bucket (141 of 291 drops).

Fixed with two fields per layout instead of one. `geodesic` stays a true metric
distance (difficulty sampling, SPL, the future progress reward); the route the
oracle *follows* comes from a clearance-penalised cost field, so it runs down the
middle of gaps. One extra solve per layout, ~20 ms.

### Discarding whole episodes contradicted the point of perturbation

`--sigma` exists to walk the robot into off-path states and label each with the
oracle's recovery action. Discarding the episode on a graze at step 700 threw
away steps 1–699 — including exactly those manufactured recovery states.

Now: truncate at the first collision, and keep timed-out episodes. Every label is
the oracle's command at the state the robot was in, so the supervision is correct
even when the outcome is missing. The classic "don't imitate trajectories that
end in a wall" argument applies to cloning the *executed* trajectory; it does not
apply when labels come from an oracle. Drops are now only: under 20 steps, or
under 0.5 m of net progress.

### The recorder leaked memory and got slower

`Collector.record` appended `ranges[i]` — a **view** — into per-env Python lists.
Two compounding faults:

- one 1.4 KB row kept the whole 2.9 MB batch frame alive, so nothing was released
  while any environment was mid-episode;
- it created `num_envs × steps × 5` tiny tensor objects, millions of them, and
  the growing live count made every GC pass slower.

That is both the climbing RSS and the climbing `ms/step` — and `ms/step` in the
progress line is a *cumulative average*, so a slow rise means the instantaneous
cost is rising much faster.

Replaced with preallocated `(num_envs, max_steps, ...)` arrays written by one
vectorized scatter per step. Memory is now a ceiling printed at startup
(5.4 GB at 4096 envs, 10.9 GB at 8192) instead of a pile. This also removed the
per-env Python loop that was capping GPU utilisation at ~60%.

### The writer overwrote a previous run

Shard numbering restarted at `bc_000`, so a second run silently overwrote the
first run's shards in place. It now scans the output directory and appends after
the highest existing index. A `SIGINT` handler was added too: previously an
interrupt lost up to a full shard of finished episodes still sitting in
`pending`.

### PhysX broadphase overflow, caused by the wall slabs

At 8192 envs: `foundLostPairsCapacity` needs 3,334,144. Not cosmetic — "the
simulation will miss interactions" means dropped contacts, so robots pass through
geometry and wheel-ground contact can be missed, while the run continues looking
healthy and the shards still verify.

Root cause was mine. A 12 m wall slab sits centred on the arena mid-line, so
relative to the env origin it spans `w/2 ± 6`: `[-4, +8]` for a 4 m arena,
`[-1, +11]` for a 10 m one — a **15 m footprint** against 14 m spacing. Adjacent
environments' slabs overlapped in the broadphase. I sized spacing against the
arena and forgot the slabs protrude past it.

Two changes: `env_spacing` 14 → 18 m (overlap-free needs `S > 12 + (w_max −
w_min)/2` = 15), and `gpu_found_lost_pairs_capacity` 2²¹ → 2²².

### Episode cap was too short

`episode_length_s = 25` is 500 steps. Measured expert speed is 0.293 m/s and
goals are sampled out to `GOAL_MAX_M = 8 m`, so the longest legitimate episode
needs ~545 steps. Those timed out and were dropped — biasing the set away from
precisely the hard layouts. Raised to 45 s (900 steps, 1.65× headroom). The tell
was already in the data: max kept episode length was 486 of 500.

### Measured

| | |
|---|---|
| 32 envs | 28.3 ms sim, 0.3 ms rec, 1,144 env-steps/s |
| 256 envs | 30.9 ms sim, 2.5 ms rec, 7,665 env-steps/s |
| 4096 envs | 65 ms sim, 59 ms rec (pre-fix), 33,043 env-steps/s |

**8× the environments cost 9% more GPU time.** The task was never GPU-bound at
these scales; the ceiling was a serial CPU section. Chasing `nvidia-smi`
utilisation is actively misleading here — more envs raises throughput while
*lowering* utilisation, because the serial fraction grows linearly while GPU work
grows sublinearly.

### A gap the fingerprint does not cover

`4b32af21edb47536` was unchanged through all of this, so shards collected under
broken physics load and merge with good ones without complaint. The fingerprint
covers how observations are *constructed*, not whether the simulation that
produced them was sound.

Worth closing before the dataset gets big enough to be reluctant to discard:
stamp shards with provenance too — Isaac version, `env_spacing`, PhysX
capacities, filter policy — and have `verify_shard.py` surface it.

### Still open

- **`Not all actuators are configured! 2 != 4`** — the Create3's wheel-drop
  suspension joints are unactuated and flop. Probably harmless on flat floor.
- `verify_shard.py` had to learn that the last recorded sample is one control
  step short of the terminal state: collection stores `(state, action)` pairs and
  evaluates success *after* stepping, so the pose that satisfies the goal is
  never recorded. The bound is `tolerance + V_MAX × DT`, not `tolerance`.
- Post-fix yield is unmeasured at scale.

## 2026-07-29 (later) — Isaac adapter bring-up

First time the adapter was actually stepped. Five defects, in the order they
surfaced; none was findable without running it.

1. **`{ENV_REGEX_NS}` is not substituted in the Direct workflow.** It is a
   manager-workflow token that `InteractiveScene` expands. Every shipped Direct
   task writes `/World/envs/env_.*/...` out in full; zero use the token.

2. **Obstacles were authored after `clone_environments(copy_from_source=False)`.**
   That call replicates whatever sits under `env_0` into every other
   environment, so the spawn loop collided with prims cloning had already made.
   Authoring moved before the clone.

3. **`_get_observations` mutated state.** It assigned `self._prev_action =
   self._action.clone()`, so last-action semantics depended on how many times
   the getter was called -- and `reset()` calls it before any action exists.
   Collapsed to a single `_action` buffer, which is already "the most recently
   commanded action": exactly what both the observation input and the oracle's
   rate limiter want. Two copies of one quantity is how they drift.

4. **Obstacles were not physics prims.** Spawned with collision properties but
   no rigid-body API, `MultiMeshRayCaster` warned that "position lookups will be
   much slower and the pose will most likely not be updated correctly when
   running in headless mode" and fell back to per-prim USD reads. That is a hang
   *and* a silent correctness bug -- obstacles the lidar never sees move.
   Rewritten as a `RigidObjectCollection` of kinematic bodies, which also
   removes the prim-path ordering hazard entirely: collection object index is
   the cfg dict's insertion order, so slot index *is* object index, and there is
   no permutation to maintain.

5. **Warp's JIT compile looks exactly like a deadlock, and I caused it
   repeatedly.** Warp compiles ray-cast kernels natively on first use, cached
   per version under `~/.cache/warp/<version>/`. The installed warp is 1.15.0
   and the only cached version was a stale 1.8.2, so every run faced a full cold
   compile: minutes, single-threaded, ~100% CPU, no Python output, and `SIGINT`
   yields no traceback because it is inside native code. Killing it discards the
   work, so each of my restarts guaranteed the next one would also "hang". This
   cost more time than any genuine bug in the project so far. Documented in the
   runbook with an explicit check.

The lesson worth keeping from (5): **before treating a silent long-running
process as hung, establish whether it is doing one-time cached work.** The tell
was single-threaded native CPU with no Python frames under `SIGINT` — that is a
compiler, not a deadlock.

### The arena walls were never spawned

Found while chasing an empty-looking viewport. `grids.rasterize` marks the
border cells occupied, and the oracle plans against that -- but nothing in Isaac
corresponded to it. The lidar therefore never saw a wall (rays left the arena
and returned max range), the robot could drive straight out, and every
demonstration that relied on the boundary was not merely hard but
**unlearnable**: the policy had no observation of the thing constraining it.

Fixed with four boundary slots (`N_WALL_SLOTS`), bringing prims per environment
to 28. The slabs are 12 m long and get *positioned*, never scaled, because
MultiMeshRayCaster bakes scale at spawn; a slab longer than the arena simply
protrudes outward. `test_wall_prims_cover_the_grid_border` asserts the slabs
cover exactly the border `rasterize` draws, so the grid stays the single
authority and the prims are proven to match it -- the same pattern intended for
C++ preprocessing parity.

### Viewport

Two reasons the scene looked empty: no walls (above), and the camera. Rooms span
`(0,0)`-`(size_x, size_y)` *from* their env origin, and `ViewerCfg.lookat`
defaults to `(0,0,0)`, so the default camera was aimed at the arena's corner.
The collector now frames env 0's actual arena after reset, which the cfg cannot
do because layouts do not exist at cfg time. The viewer's tracking callback only
re-applies for `asset_root`/`asset_body`, so setting it once leaves manual
navigation free.

### Verified on a real 4-environment run

Scene builds; lidar returns `(4, 720)` with 40.4% finite hits and 42.4% of bins
carrying a return; all robots spawn in free space.

### Still open

- The bring-up checks have not completed past the lidar stage; the warp warmup
  was still compiling at the time of writing.
- **`Not all actuators are configured! 2 != 4`** — the Create3's wheel-drop
  suspension joints are unactuated and will flop. Probably harmless on flat
  floor, but they should get a stiff actuator or be locked at import.
- Per-environment layout spread is asserted by the check but has not yet run.

## 2026-07-29 — Reset to first principles; layout, oracle, dataset, Isaac adapter

### Reset

The previous build was archived to `archive/v1-numpy-pipeline` (pushed to
origin) and `main` was cleared. Nothing was deleted that is not still reachable
on that branch.

The trigger was a question about the split between simulator and non-simulator
code, and the answer that came out of it reframed the rebuild: room generation
was never the problem — it already ran inside Isaac. The real gap was that BC
and DAgger collection ran **only** in a numpy kinematic environment
(`collect_episodes` → `NavEnv`), while PPO ran in Isaac. The deployed path was
therefore: pretrain on one sensor model, fine-tune on another. For depth that is
especially bad, since the numpy env ray-casts analytically against boxes while
Isaac renders. This rebuild collects BC data in the same simulator PPO will use.

### Design decisions taken this session

Four changes to the proposed plan, all adopted:

1. **C++ preprocessing is deployment-side, not collection-side.** Isaac hands
   lidar over as a GPU-resident `(num_envs, beams)` tensor; routing it through
   C++ costs a device→host→device round trip per step to save microseconds of
   arithmetic. The C++ implementation exists because the *robot* needs it, and a
   parity test will pin the two together. Preprocessing during training is
   batched torch, on device.

2. **The dataset stores raw, never processed or noisy.** Shards hold raw ranges,
   beam bearings, true poses, and oracle commands. Noise and binning happen in
   the loader. Consequences: every epoch draws a fresh corruption of the same
   scan (free regularization instead of one frozen sample per state), and
   retuning noise or changing `LIDAR_BINS` becomes a loader edit rather than a
   recollection run.

3. **Collection perturbs the executed action from day one.** Pure oracle-driven
   collection only ever visits states the oracle put itself in, so the policy
   inherits no recovery behaviour and more expert data does not fix it. The
   collection loop is built to take a "who drives" argument so BC, DART-style
   perturbation, and DAgger are one code path.

4. **The goal is in the observation** as (distance / `GOAL_MAX_M`, sin bearing,
   cos bearing) in the robot frame. Without it the task is not learnable — two
   identical scans with opposite goals have different correct actions.

### `spec.py` — the rule

Challenged as unnecessary; kept, at ~85 lines, under an explicit rule: **a
constant lives here iff at least two modules read it.** Room parameters moved to
`rooms.py`, noise ranges to `noise.py`, both single-consumer. What survived is
read by four modules apiece. `fingerprint()` stayed because `dataset.py` stamps
it and refuses mismatched shards — a dataset collected at 180 bins and loaded by
a policy expecting 120 has compatible-looking shapes right until it doesn't.

### Built

| Module | Role |
|---|---|
| `sim2edge/spec.py` | Shared constants + fingerprint. Stdlib only. |
| `sim2edge/grids.py` | Rasterize, exact EDT clearance, geodesic field, flow field. |
| `sim2edge/rooms.py` | Layout sampling into fixed-length slot arrays. |
| `sim2edge/preprocess.py` | Batched torch: angle-binned min-pool, goal features. |
| `sim2edge/noise.py` | Load-time sensor and odometry corruption. |
| `sim2edge/oracle.py` | Batched flow-walk + lookahead controller. |
| `sim2edge/dataset.py` | Raw shard I/O, fingerprint-checked, fresh noise per epoch. |
| `isaaclab_env/nav_task.py` | Isaac Lab adapter. |
| `tools/convert_tb4.py` | TB4 Lite xacro → URDF → USD. |

96 tests, 1 skipped (needs Isaac in-process).

Two design choices worth remembering:

- **Feasibility is guaranteed by construction, not rejection.** The goal is
  placed first, one geodesic solve labels every cell with its true path length,
  and the start is drawn from cells already in the required range. One solve
  yields reachability and difficulty together. Difficulty is therefore geodesic
  distance, not straight-line — a goal 3 m away through a wall is a harder
  episode than one 6 m down an open corridor.

- **The flow field is precomputed on CPU.** Following the geodesic gradient on
  device would mean an 8-way comparison plus the corner-cut test per env per
  tick. Precomputing "which neighbour is next" once per layout turns the
  oracle's path walk into a chain of gathers with no branches.

### Bugs found by the tests

**The oracle stranded itself.** Rolling out a real layout, the robot tracked into
a cell with clearance below the robot radius, where the flow field self-looped.
Its lookahead point became its own position, giving a meaningless bearing, and
it spun at ω=1.9 for 900 steps. Not a tuning issue — the field only guided from
free cells, but a robot leaves them constantly, and DART perturbation *puts it
there on purpose*. Fixed by pointing every non-free cell at its nearest free
neighbour via one EDT call, so the first hop climbs back onto the path.

**A 538 MB allocation per oracle step.** `pool.flow[layout]` materialized a full
`(N, H*W)` copy of the fields to then read one element per row. Indexing both
axes at once made the step 156× faster (48.6 ms → 0.31 ms at 2048 envs). Would
have surfaced as an OOM on GPU long after anyone was looking at the oracle.

### Isaac Lab 0.54.4 findings that changed the design

Read out of the installed source, not documentation:

1. **Plain `RayCaster` cannot see moving obstacles.** It rejects more than one
   mesh prim, takes only the first `Mesh` child it finds, and bakes the world
   transform into a static warp mesh at init. Obstacles repositioned at reset
   would be invisible to the lidar. `MultiMeshRayCaster` tracks transforms and
   is what the adapter uses.

2. **It tracks pose but bakes scale.** `mesh.apply_scale` runs once at parse;
   only `_mesh_positions_w` / `_mesh_orientations_w` update per step. So
   obstacle *size cannot change at reset*. `rooms.py` was rewritten around a
   discrete size ladder: 24 prims spawned once at fixed sizes, and a layout
   chooses which slots to use and where. Slot index is a prim identity, not a
   description. Yaw *is* tracked per step, so rotation was added as free shape
   diversity to compensate — which also required rotated-box rasterization.

3. **There is no Create3 or TurtleBot asset in `isaaclab_assets`.** The previous
   plan assumed one existed. The robot now comes from
   `ros-jazzy-turtlebot4-description` via `tools/convert_tb4.py`.

### Robot geometry, from the ROS description

Taken from `irobot_create_description` and `turtlebot4_description`, verified
against the expanded URDF:

| | |
|---|---|
| Body radius | 0.164 m (`ROBOT_RADIUS_M` = 0.18, inflated for planning) |
| Wheel separation | 0.233 m |
| Wheel radius | 0.03575 m |
| `base_link_z_offset` | 0.0642 m |
| RPLIDAR mount | (0.0039, 0, 0.1395) m, **yaw +π/2** |
| OAK-D Lite mount | (−0.0371, 0, 0.1859) m |

**The lidar is bolted on rotated a quarter turn.** Beam bearings arrive 90° off
the robot's forward axis. The adapter mounts the sensor with that rotation and
undoes it once when building beam angles — applied once, never twice. The goal
bearing is in the robot frame, so a scan left in the sensor frame would put
every obstacle at right angles to where the policy believes it is. This is in
the fingerprint because it changes how the observation is constructed, and
`test_urdf_lidar_mount_matches_the_spec` fails if a package update moves it.

### Two ordering hazards closed

- **Prim view ordering.** USD stage traversal orders paths lexicographically,
  and `env_10` sorts before `env_2`. Assuming env-major order would write
  layouts into the wrong environments and look like a sampler bug. The adapter
  parses `view.prim_paths` and builds the permutation explicitly.
- **Wheel joint ordering.** `.*wheel_joint` matches both wheels but does not
  specify the order. Swapping left for right yields a robot that turns the wrong
  way, which reads as a broken controller. Resolved by exact name with
  `preserve_order=True`, plus an assertion.

### Asset conversion — done and verified

`tools/convert_tb4.py` runs end to end. Two ordering traps on the way:

- **`ModuleNotFoundError: No module named 'pxr'`.** The USD Python bindings ship
  inside Isaac Sim's kit runtime and are not importable until `AppLauncher` puts
  them on `sys.path`. Importing `isaaclab.sim.converters` cold fails, and it
  reads as a missing dependency when it is purely an ordering problem.
  `AppLauncher` itself imports fine beforehand -- it is the bootstrap. The
  converter now launches headless first and imports everything else after, so
  `--help` and `--urdf-only` still skip the ~30 s startup.
- **A scratch file named `inspect.py` broke the bootstrap** with a bogus
  "circular import" on `isaaclab.app`. Isaac's launcher imports the stdlib
  `inspect`, and the script's own directory sorts first on `sys.path`.

The produced USD has articulation root `/turtlebot4/base_link`, exactly the two
revolute joints `left_wheel_joint` and `right_wheel_joint` that the adapter
binds by name, and an `rplidar_link` prim. `merge_fixed_joints=True` folds the
lidar link into `base_link`, which is fine — the adapter mounts the sensor by
explicit offset from `spec.py`, not by attaching to the link.

### Not done

- Superseded by the bring-up entry above: the adapter has now been stepped.
- The C++ node and its parity test do not exist. When they do, the parity test
  must cover **every** implementation, not two of three — that gap is what
  produced the `invalid_fill` bug in the previous build.
- No reward function. `_get_rewards` returns zeros; BC does not need it and PPO
  will replace it with geodesic progress.
- Throughput of `MultiMeshRayCaster` tracking ~50k meshes is unmeasured and is
  the largest remaining risk in the design.
