## 2026-07-29 (latest) — First full collection runs; yield, memory, PhysX

The pipeline ran end to end and produced verified-good shards. None of the
following was visible at 32 envs.

### Yield figure was wrong

Sampled a probe at step 600 (25/256 envs finished) and reported 76% yield.
Episodes that finish first are the ones that succeed — failures run on until
they collide or hit the step cap, so they hadn't been counted yet. True figure
was **8.6%**, worse than the 12% baseline. "0 timeouts" was the same
artifact: a timeout *cannot* appear early, by construction.

**Rule:** yield is meaningless until `kept + dropped` is several multiples of
`num_envs`.

### Collision tested against the planning radius, not the body

`is_free` thresholded at `ROBOT_RADIUS_M = 0.18`, but the Create3's body
radius is 0.164 — the difference is deliberate planning margin. Any pose in
that 16 mm band was reported as a collision with nothing touching, sticky for
the whole episode. Added `BODY_RADIUS_M = 0.164` and `Room.body_free`,
deliberately excluded from the fingerprint since it changes episode
selection, not observation construction.

### The oracle rode the boundary it planned to

Paths ran along the 0.18 m planning edge, where the flow field's recovery
pushes back while the lookahead pulls forward — a limit cycle that both
grazed geometry and never finished (141 of 291 drops). Fixed with two fields
per layout: `geodesic` stays a true metric distance (difficulty, SPL,
progress reward), while the route the oracle *follows* comes from a
clearance-penalised cost field that runs down the middle of gaps.

### Discarding whole episodes contradicted the point of perturbation

`--sigma` walks the robot into off-path states and labels each with the
oracle's recovery action; discarding the episode on a graze at step 700 threw
away exactly those states. Now: truncate at the first collision, keep
timed-out episodes. Every label is the oracle's command at the state the
robot was in, so supervision is correct even when the outcome is missing —
cloning the *executed* trajectory is not the same as cloning oracle labels.
Drops are now only: under 20 steps, or under 0.5 m of net progress.

### The recorder leaked memory and got slower

`Collector.record` appended `ranges[i]` — a **view** — into per-env Python
lists. One 1.4 KB row kept the whole 2.9 MB batch frame alive, and it created
millions of tiny tensor objects whose growing live count made every GC pass
slower. That's both the climbing RSS and the climbing `ms/step` (a
*cumulative average*, so a slow rise means the instantaneous cost is rising
much faster). Replaced with preallocated `(num_envs, max_steps, ...)` arrays
written by one vectorized scatter per step. Memory is now a ceiling printed
at startup (5.4 GB at 4096 envs, 10.9 GB at 8192).

### The writer overwrote a previous run

Shard numbering restarted at `bc_000` on every run. Now scans the output
directory and appends after the highest existing index. Added a `SIGINT`
handler — previously an interrupt lost up to a full shard of finished
episodes still in `pending`.

### PhysX broadphase overflow, caused by the wall slabs

At 8192 envs: `foundLostPairsCapacity` needs 3,334,144 — not cosmetic, it
means dropped contacts (robots pass through geometry) while the run still
looks healthy. Root cause: a 12 m wall slab centred on the arena mid-line
spans `w/2 ± 6`, a 15 m footprint against 14 m env spacing, so adjacent
slabs overlapped in the broadphase. Fixed: `env_spacing` 14 → 18 m
(overlap-free needs `S > 12 + (w_max − w_min)/2` = 15), and
`gpu_found_lost_pairs_capacity` 2²¹ → 2²².

### Episode cap was too short

`episode_length_s = 25` is 500 steps. Measured expert speed is 0.293 m/s and
goals go out to `GOAL_MAX_M = 8 m`, so the longest legitimate episode needs
~545 steps — those timed out and were dropped, biasing away from hard
layouts. Raised to 45 s (900 steps). Max kept episode length was already 486
of 500.

### Measured

| | |
|---|---|
| 32 envs | 28.3 ms sim, 0.3 ms rec, 1,144 env-steps/s |
| 256 envs | 30.9 ms sim, 2.5 ms rec, 7,665 env-steps/s |
| 4096 envs | 65 ms sim, 59 ms rec (pre-fix), 33,043 env-steps/s |

**8× the environments cost 9% more GPU time** — never GPU-bound at these
scales; the ceiling was a serial CPU section, so `nvidia-smi` utilisation is
actively misleading (more envs raises throughput while *lowering*
utilisation).

### A gap the fingerprint does not cover

`4b32af21edb47536` was unchanged through all of this, so shards collected
under broken physics merge with good ones without complaint — the
fingerprint covers observation construction, not simulation soundness. Worth
closing before the dataset is big enough to be reluctant to discard: stamp
shards with provenance (Isaac version, `env_spacing`, PhysX capacities,
filter policy) and have `verify_shard.py` surface it.

### Still open

- `Not all actuators are configured! 2 != 4` — Create3 wheel-drop suspension
  joints are unactuated and flop; probably harmless on flat floor.
- `verify_shard.py` learned the last recorded sample is one control step
  short of the terminal state: collection stores `(state, action)` and
  evaluates success *after* stepping, so the goal-satisfying pose is never
  recorded. Bound is `tolerance + V_MAX × DT`, not `tolerance`.
- Post-fix yield is unmeasured at scale.

## 2026-07-29 (later) — Isaac adapter bring-up

First time the adapter was actually stepped. Five defects, in the order they
surfaced; none was findable without running it.

1. **`{ENV_REGEX_NS}` is not substituted in the Direct workflow.** It's a
   manager-workflow token that `InteractiveScene` expands; every shipped
   Direct task writes `/World/envs/env_.*/...` out in full.

2. **Obstacles were authored after `clone_environments(copy_from_source=False)`**,
   which replicates whatever sits under `env_0` into every other environment
   — so the spawn loop collided with prims cloning had already made.
   Authoring moved before the clone.

3. **`_get_observations` mutated state**, assigning `self._prev_action =
   self._action.clone()`, so last-action semantics depended on how many
   times the getter was called — and `reset()` calls it before any action
   exists. Collapsed to a single `_action` buffer.

4. **Obstacles were not physics prims** — spawned with collision properties
   but no rigid-body API, so `MultiMeshRayCaster` fell back to slow per-prim
   USD reads (a hang risk) and, worse, obstacles the lidar never sees move (a
   silent correctness bug). Rewritten as a `RigidObjectCollection` of
   kinematic bodies, which also fixes prim-path ordering: slot index *is*
   object index.

5. **Warp's JIT compile looks exactly like a deadlock, and it cost more time
   than any genuine bug in the project so far.** Warp compiles ray-cast
   kernels natively on first use, cached per version. The installed warp was
   1.15.0 but the only cache was a stale 1.8.2, so every run faced a full
   cold compile: minutes, single-threaded, ~100% CPU, no Python output, and
   `SIGINT` gives no traceback (native code) — so killing it discards the
   work and guarantees the next run "hangs" too. **Lesson: before treating a
   silent long-running process as hung, check whether it's one-time cached
   work** — single-threaded native CPU with no Python frames under `SIGINT`
   is a compiler, not a deadlock. Documented in the runbook.

### The arena walls were never spawned

Found while chasing an empty-looking viewport. `grids.rasterize` marks
border cells occupied and the oracle plans against that, but nothing in
Isaac corresponded to it — rays left the arena and returned max range, the
robot could drive straight out, and every demonstration relying on the
boundary was **unlearnable** (no observation of the constraint). Fixed with
four boundary slots (`N_WALL_SLOTS`, 28 prims/env). Slabs are positioned,
never scaled (`MultiMeshRayCaster` bakes scale at spawn).
`test_wall_prims_cover_the_grid_border` asserts the slabs match what
`rasterize` draws.

### Viewport

Rooms span `(0,0)`–`(size_x, size_y)` from their env origin, and
`ViewerCfg.lookat` defaults to `(0,0,0)` — camera aimed at the arena corner.
The collector now frames env 0's actual arena after reset (layouts don't
exist at cfg time).

### Verified on a real 4-environment run

Scene builds; lidar returns `(4, 720)` with 40.4% finite hits and 42.4% of
bins carrying a return; all robots spawn in free space.

### Still open

- Bring-up checks hadn't completed past the lidar stage at time of writing.
- `Not all actuators are configured! 2 != 4` (see above).
- Per-environment layout spread is asserted but hadn't yet run.

## 2026-07-29 — Reset to first principles; layout, oracle, dataset, Isaac adapter

### Reset

The previous build was archived to `archive/v1-numpy-pipeline` and `main`
cleared. The trigger was a question about the sim/non-sim code split: room
generation was never the problem (already ran inside Isaac). The real gap
was that BC/DAgger collection ran **only** in a numpy kinematic environment
while PPO ran in Isaac — pretrain on one sensor model, fine-tune on another,
especially bad for depth since the numpy env ray-casts analytically against
boxes while Isaac renders. This rebuild collects BC data in the same
simulator PPO uses.

### Design decisions taken this session

1. **C++ preprocessing is deployment-side, not collection-side.** Routing
   Isaac's GPU-resident lidar tensor through C++ during training costs a
   device→host→device round trip to save microseconds; the C++ path exists
   because the *robot* needs it, pinned to training by a parity test.
2. **The dataset stores raw, never processed or noisy.** Noise and binning
   happen in the loader — free regularization per epoch, and retuning noise
   or `LIDAR_BINS` becomes a loader edit, not a recollection.
3. **Collection perturbs the executed action from day one.** Pure
   oracle-driven collection only visits states the oracle put itself in, so
   the policy never learns recovery. The loop takes a "who drives" argument
   so BC, DART-style perturbation, and DAgger are one code path.
4. **The goal is in the observation** as (distance / `GOAL_MAX_M`, sin
   bearing, cos bearing) in the robot frame — without it two identical scans
   with opposite goals have different correct actions.

### `spec.py` — the rule

Kept at ~85 lines under an explicit rule: **a constant lives here iff at
least two modules read it.** Room parameters moved to `rooms.py`, noise
ranges to `noise.py` (single-consumer each). `fingerprint()` stayed —
`dataset.py` refuses mismatched shards, since a corpus collected at 180 bins
loaded by a policy expecting 120 has compatible-looking shapes right until it
doesn't.

### Built

| Module | Role |
|---|---|
| `sim2edge/spec.py` | Shared constants + fingerprint. Stdlib only. |
| `sim2edge/grids.py` | Rasterize, exact EDT clearance, geodesic field, flow field. |
| `sim2edge/rooms.py` | Layout sampling into fixed-length slot arrays. |
| `sim2edge/preprocess.py` | Batched torch: angle-binned min-pool, goal features. |
| `sim2edge/noise.py` | Load-time sensor and odometry corruption. |
| `sim2edge/oracle.py` | Batched flow-walk + lookahead controller. |
| `sim2edge/dataset.py` | Raw shard I/O, fingerprint-checked, fresh noise per epoch. |
| `isaaclab_env/nav_task.py` | Isaac Lab adapter. |
| `tools/convert_tb4.py` | TB4 Lite xacro → URDF → USD. |

96 tests, 1 skipped (needs Isaac in-process).

Two design choices worth remembering:

- **Feasibility is guaranteed by construction, not rejection.** The goal is
  placed first, one geodesic solve labels every cell with true path length,
  and the start is drawn from cells already in range — difficulty is
  geodesic distance, not straight-line.
- **The flow field is precomputed on CPU.** Following the geodesic gradient
  on device per-tick would mean an 8-way comparison plus corner-cut test per
  env per tick; precomputing "which neighbour is next" once per layout turns
  the oracle's path walk into a branchless chain of gathers.

### Measured

| | |
|---|---|
| Layout pool build | 21 ms/layout — 512 layouts in ~11 s, once |
| Oracle step, 2048 envs | 0.31 ms CPU (0.15 µs/env) |
| Shard size | 610 B/step → 0.6 GB per million steps |
| Loader throughput | 368k samples/s CPU, noise + binning included |

### Bugs found by the tests

**The oracle stranded itself.** Rolling out a real layout, the robot tracked
into a cell with clearance below the robot radius, where the flow field
self-looped — its lookahead point became its own position, giving a
meaningless bearing, and it spun at ω=1.9 for 900 steps. Not a tuning issue:
a robot leaves free cells constantly, and DART perturbation puts it there on
purpose. Fixed by pointing every non-free cell at its nearest free neighbour
via one EDT call.

**A 538 MB allocation per oracle step.** `pool.flow[layout]` materialized a
full `(N, H*W)` copy of the fields to read one element per row. Indexing
both axes at once made the step 156× faster (48.6 ms → 0.31 ms at 2048
envs) — would have surfaced as an OOM on GPU long after anyone was looking
at the oracle.

### Isaac Lab 0.54.4 findings that changed the design

Read out of the installed source, not documentation:

1. **Plain `RayCaster` cannot see moving obstacles** — rejects more than one
   mesh prim, takes only the first `Mesh` child, bakes the world transform
   into a static warp mesh at init. `MultiMeshRayCaster` tracks transforms
   and is what the adapter uses.
2. **It tracks pose but bakes scale** (`mesh.apply_scale` runs once at
   parse) — obstacle *size cannot change at reset*. `rooms.py` was rewritten
   around a discrete size ladder: 24 prims spawned once at fixed sizes, a
   layout chooses which slots to use and where. Yaw *is* tracked per step, so
   rotation was added as free shape diversity, requiring rotated-box
   rasterization.
3. **There is no Create3 or TurtleBot asset in `isaaclab_assets`.** The robot
   comes from `ros-jazzy-turtlebot4-description` via `tools/convert_tb4.py`.

### Robot geometry, from the ROS description

Taken from `irobot_create_description` and `turtlebot4_description`,
verified against the expanded URDF:

| | |
|---|---|
| Body radius | 0.164 m (`ROBOT_RADIUS_M` = 0.18, inflated for planning) |
| Wheel separation | 0.233 m |
| Wheel radius | 0.03575 m |
| `base_link_z_offset` | 0.0642 m |
| RPLIDAR mount | (0.0039, 0, 0.1395) m, **yaw +π/2** |
| OAK-D Lite mount | (−0.0371, 0, 0.1859) m |

**The lidar is bolted on rotated a quarter turn.** Beam bearings arrive 90°
off the robot's forward axis. The adapter mounts the sensor with that
rotation and undoes it once when building beam angles. This is in the
fingerprint (changes observation construction); `test_urdf_lidar_mount_matches_the_spec`
fails if a package update moves it.

### Two ordering hazards closed

- **Prim view ordering.** USD stage traversal is lexicographic (`env_10`
  sorts before `env_2`); assuming env-major order would silently write
  layouts into the wrong environments. The adapter parses `view.prim_paths`
  and builds the permutation explicitly.
- **Wheel joint ordering.** `.*wheel_joint` matches both wheels without
  specifying order — swapping left/right yields a robot that turns the
  wrong way. Resolved by exact name with `preserve_order=True`, plus an
  assertion.

### Asset conversion — done and verified

`tools/convert_tb4.py` runs end to end. Two ordering traps:

- **`ModuleNotFoundError: No module named 'pxr'`** — USD Python bindings
  ship inside Isaac Sim's kit runtime, not importable until `AppLauncher`
  puts them on `sys.path`. The converter now launches headless first and
  imports everything else after, so `--help`/`--urdf-only` still skip the
  ~30 s startup.
- **A scratch file named `inspect.py` broke the bootstrap** with a bogus
  "circular import" on `isaaclab.app` — Isaac's launcher imports the stdlib
  `inspect`, and the script's own directory sorts first on `sys.path`.

Produced USD has articulation root `/turtlebot4/base_link`, the two revolute
joints the adapter binds by name, and an `rplidar_link` prim.
`merge_fixed_joints=True` folds the lidar link into `base_link`, fine since
the adapter mounts the sensor by explicit offset from `spec.py`.

### Not done

- Superseded by the bring-up entry above: the adapter has now been stepped.
- The C++ node and its parity test do not exist yet. When they do, the

- No reward function yet; `_get_rewards` returns zeros.
- Throughput of `MultiMeshRayCaster` tracking ~50k meshes is unmeasured and
